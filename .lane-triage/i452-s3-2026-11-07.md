## S3 CALIBRATION INPUTS - fresh session-start specimens from the laptop lanes (2026-11-07)

Mission item 3 for the harness laptop lane. These are *inputs*, not per-field bars: what a live FreeBuff session actually presents on this machine, measured at session start from inside the session. Collected 2026-11-07 ~20:15 local; seat opened on `main` @ `b4b341a`.

### S1. Display geometry and what the capture actually returns

| Fact | Value | Method |
|---|---|---|
| Physical screen | **1920 x 1200** | `GetSystemMetrics(0/1)` after `SetProcessDPIAware()` |
| Scale factor | **120 dpi = 125%** | `GetDeviceCaps(LOGPIXELSX)` on the screen DC |
| `capture_screen()` output | **1536 x 960 PNG**, 185,020 bytes | `driver_core.osal.capture_screen()` with `DRIVER_SCREEN_OUT` set; dimensions read from the PNG IHDR |

Calibration consequence: **1920 / 1.25 = 1536**, so the capture is in *logical* pixels while the window coordinates an automation API hands back are in *physical* pixels. Any bar phrased in raw pixels must name which space it is in, or it will be off by 25% on exactly this machine. This reproduces the 2026-11-06 specimen exactly (same 1536x960), so the scaling is stable across days and app restarts.

### S2. The refusal frame is first-class and must be expected

Without `DRIVER_SCREEN_OUT`, `capture_screen()` returns `path=None` with the detail **`DRIVER_SCREEN_OUT is not set; cannot capture`**. A driver that treats "no file" as a vision-model problem will describe a file that does not exist. The calibration input: the capture path is an explicit opt-in, and its absence is a routing instruction, not an error to retry.

### S3. Foreground description - what is readable at session start, and what is not

```
foreground_app  = Freebuff
```

So of the eight launch-gate fields the road wants, only **app identity** (app + window title) is readable through this path today. There is no text, no control inventory, no focus state. That is the gap S3's per-field negatives have to be measured against.

### S4. Window identity is not stable - two independent ways it collides or drifts

Measured window inventory this session (`EnumWindows`, visible + titled only): **7 windows, 3 of them share `Chrome_WidgetWin_1`** - `Freebuff: The free coding agent`, a Chrome window, and `ChatGPT`.

| Window | Class | Rect |
|---|---|---|
| Freebuff | `Chrome_WidgetWin_1` | **(60, 6, 1860, 1137)** |
| Chrome (research tab) | `Chrome_WidgetWin_1` | (-9, -9, 1929, 1149) |
| ChatGPT | `Chrome_WidgetWin_1` | (0, 0, 1920, 1140) |

Two calibration inputs fall straight out:

1. **Class is not an identity key.** `Chrome_WidgetWin_1` matches three different apps. Title-prefix `Freebuff:` is currently the only discriminator, and it is user-visible text, not a stable handle.
2. **Geometry drifts between sessions.** Yesterday's specimen recorded the FreeBuff window at `[48, 5, 1488, 910]`, 1440x905; today it is `(60, 6, 1860, 1137)`, 1800x1131. Same app, same machine, different maximize state. A bar that pins a rect will pass or fail on window state, not on driver behaviour - exactly the environment-truth defect #454 is about.
