# Isolate request handling from log-file write failures

Part of #683, finding 18 (P2). Verified against `main` `8fc28a0e` on
2026-11-25: still present.

## What is present

`harness/server.py:1602-1616`, `UiRequestHandler.log_message`:

```python
line = _CREDENTIAL_IN_LOG_RE.sub(r"\g<name>REDACTED", format % args)
sys.stderr.write(f"[ui] {line}\n")
...
log = getattr(getattr(self, "server", None), "serve_log", None)
if log is not None:
    log.write(f"[ui] {line}")
```

Neither write is guarded.

## Why it matters

`BaseHTTPRequestHandler.send_response()` calls `log_request()` before it sends
headers. If the log filesystem fills or a flush raises `OSError`, the exception
propagates out of `send_response` and the connection closes with no response -
`GET /` included. The error path uses the same logger, so the handler cannot
report the failure either. The review reproduced `RemoteDisconnected` by making
the attached log raise `OSError(28, "No space left on device")`.

Both CLI entry points attach this sink by default, so a full disk makes the
whole UI unavailable rather than producing a response with a logging warning.

## Requested fix

Catch write failures at the logging boundary: report the failure once on
stderr (without recursing into the failing sink), mark the sink degraded so the
message is not repeated per request, and let the HTTP response proceed.

## Acceptance

- With a log sink that raises `OSError`, `GET /` still returns a response.
- The failure is reported once on stderr, not once per request.
- A hermetic test attaches a raising sink and asserts the response status.
