# Fingerprint the retained ledger segments in the snapshot cache

Part of #683, finding 15 (P2). Verified against `main` `8fc28a0e` on
2026-11-25: still present.

## What is present

`harness/server.py` builds the `/api/snapshot` cache key from the active ledger
file only:

```python
st = os.stat(settings.ledger_path)
fingerprint = (str(settings.ledger_path), st.st_size,
               getattr(st, "st_mtime_ns", None))
```

That key is passed to `UiState.cached(("site_snapshot",) + fingerprint, build)`
at `harness/server.py:2358`.

`AutonomyLedger._ledger_paths()` (`harness/ledger.py:185`) verifies the ledger
from the active file **and** its rotated retained segments. The two inputs do
not agree: a retained segment can change, or be corrupted, without moving the
active file's size or mtime.

## Why it matters

A broken retained chain is exactly the condition `build()` refuses on:

```python
ok, _bad = ledger.verify()
if not ok:
    raise HarnessError("ledger hash chain failed verification; refusing snapshot")
```

Because the fingerprint does not cover the segments, that refusal is skipped for
the whole TTL after a segment changes, and `/api/snapshot` keeps serving a
payload that the fresh verification would reject. The reproduction recorded in
the review: touching a rotated segment made a fresh `ledger.verify()` return
`(False, 1)` while the snapshot still returned the cached payload.

## Requested fix

Fingerprint every path `_ledger_paths()` reads, not just the active file -
for example a tuple of `(path, size, mtime_ns)` per path, ordered the way the
ledger orders them - so any segment change re-verifies before serving.

## Acceptance

- Changing a retained segment changes the snapshot cache key.
- After such a change the next `/api/snapshot` re-runs `verify()` instead of
  serving the cached payload.
- A hermetic test rotates a ledger, mutates the retained segment, and asserts
  the snapshot refuses rather than serving stale data.
