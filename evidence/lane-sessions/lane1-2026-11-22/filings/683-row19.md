# Verify the served package belongs to the repository being identified

Part of #683, finding 19 (P2). Verified against `main` `8fc28a0e` on
2026-11-25: still present.

## What is present

`harness/server.py:1568-1577`:

```python
root = Path(repo_root) if repo_root is not None \
    else Path(__file__).resolve().parent.parent
...
ident = {"version": HARNESS_VERSION, "commit": _git_describe(root)}
```

`_git_describe` (`harness/server.py:1544`) runs `git -C <root> describe
--always --dirty` and returns the result whenever the command succeeds. It
never checks that the repository it landed in contains the Harness source that
is actually loaded.

## Why it matters

When Harness is installed as a wheel into a `.venv` inside another project's
git checkout, `root` is that `site-packages` directory and `git -C` walks up to
the enclosing project's repository. The identity then reports the unrelated
application's commit, on every response header
(`X-Harness-Commit`) and in the startup message - a confident statement about
code that is not being served. The review reproduced exactly this: the wrong
commit was reported where `unknown` was correct.

The diagnostic this adds (#587) is only worth having if it cannot name the
wrong tree.

## Requested fix

Confirm the resolved repository actually tracks the loaded Harness source
before accepting its commit - for example require that `git -C <root> ls-files`
or the repository top level corresponds to the package's source root. When it
does not, keep the package version and report `unknown`.

## Acceptance

- A wheel installed inside another project's checkout reports `unknown`, not
  the enclosing repository's commit.
- A source checkout still reports its own commit and dirty flag.
- A hermetic test builds both layouts with `repo_root` and asserts each.
