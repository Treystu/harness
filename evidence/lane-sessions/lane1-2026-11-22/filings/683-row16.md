# Evict superseded snapshot cache entries

Part of #683, finding 16 (P2). Verified against `main` `8fc28a0e` on
2026-11-25: still present.

## What is present

`harness/server.py:1284` creates the cache as a plain dict:

```python
self._api_cache = {}
```

and `UiState.cached` (`harness/server.py:1320-1334`) only looks at expiration
for the key it is asked for:

```python
now = time.time()
with self.lock:
    hit = self._api_cache.get(key)
    if hit and now - hit[0] < self.CACHE_TTL:
        return hit[1]
value = build()
with self.lock:
    self._api_cache[key] = (now, value)
```

Nothing ever removes an entry. Rows whose key is never requested again - every
historical `("site_snapshot",) + fingerprint` - stay in the dict forever.

## Why it matters

The snapshot key embeds the ledger fingerprint, so each ledger write that lands
between two Proof visits creates a new key. A long-running `harness serve`
therefore retains one full aggregated snapshot payload per version, and memory
grows with ledger activity and Proof visits rather than with the number of live
endpoints. Nothing bounds it and nothing reports it.

## Requested fix

Make the snapshot path evict: keep only the current fingerprint for
`site_snapshot`, or give `_api_cache` a bounded size with expiry-driven
removal of superseded keys on insert. Other short-TTL endpoints should keep
their current behaviour.

## Acceptance

- Inserting a snapshot entry under a new fingerprint removes or bounds the
  superseded ones.
- A hermetic test inserts N distinct snapshot fingerprints and asserts the
  cache holds a bounded number of entries.
- Existing cache-hit behaviour inside the TTL is unchanged.
