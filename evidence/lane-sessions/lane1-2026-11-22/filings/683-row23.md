# Require media-specific identity evidence before accepting a JSON error

Part of #683, finding 23 (P2). Verified against `main` `8fc28a0e` on
2026-11-25: still present.

## What is present

`harness/media_client.py:136-142`, inside `identify_service`:

```python
if _MEDIA_PROBE_KEYS & set(payload):
    return "media"
if "error" in payload or "detail" in payload:
    # The service's own note, e.g. its credential challenge. A bare 401
    # with no body is not this case and stays unidentified.
    return "media"
```

Any JSON object carrying `error` or `detail` is classified as the media
service, with no media-specific marker in it.

## Why it matters

`MediaAdapter._ensure_identified()` treats `"media"` as proof and sets
`self._identified = True`; every later call then sends `X-Media-Token`. An
unrelated loopback service answering `/v1/balance` with a generic JSON error -
HTTP 404 `{"detail": "Not Found"}` for example - is therefore positively
identified as media, and the token is sent to it. The review reproduced it with
a local HTTP server: a credential-free probe, then a token-bearing
`POST /v1/jobs`.

That defeats the guard's contract, which is that no credential leaves the
process until the endpoint proves what it is (#566).

## Requested fix

Accept only service-specific evidence: a media-only marker (an existing key in
`_MEDIA_PROBE_KEYS`, a media-specific header, or a recognizable auth challenge
shape) rather than the presence of any `error`/`detail` field. Everything else
stays `unknown` and the adapter raises without sending a token.

## Acceptance

- `{"detail": "Not Found"}` from a loopback probe yields `unknown`, and no
  `X-Media-Token` is sent afterwards.
- A real media challenge or media marker still yields `media`.
- Hermetic tests cover both, asserting that no token-bearing request follows
  an unidentified probe.
